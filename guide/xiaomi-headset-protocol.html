小米耳机协议：MMA 与 RCSP ​

小米 / Redmi 耳机并不是只有一种控制协议。当前仓库包含两条已经落地的实现路径：

路径设备包适用设备能否直接复制
MMAxiaomi.mmaXiaomi / Redmi Buds 家族的通用回退配置只适合作为起点，型号差异仍需实测
RCSP TargetInfoxiaomi.redmi_buds6Redmi Buds 6 精确型号适合作为同系列精确型号的参考

两条路径共用 FE DC BA ... EF 外壳，但认证、control 字节、命令码和通知方向不同。不要只按“小米耳机”名称复制其中一个设备包。

精确型号包使用更高的 matcher 优先级，因此会在通用规则之前命中。新增型号时优先复制结构最接近的精确包，并重新测量命令和字段，不要把一套未知型号直接套进通用包。

RFCOMM 连接 ​

两个样例都先尝试小米控制服务：

text
0000FD2D-0000-1000-8000-00805F9B34FB
1

找不到该服务时再尝试兼容候选：

text
00001101-0000-1000-8000-008584D01810
1

transport 应为 type: "rfcomm"、bonded: true，且不要填写 GATT characteristic。当前 Android RFCOMM 适配层只做 SDP UUID 连接；如果某型号既不广播 FD2D，也不能通过兼容 UUID 连接，固定 channel 6 兜底尚未实现。

共用帧外壳 ​

一般请求：

text
FE DC BA | control | command | lenHi lenLo | sequence | payload | EF
1

一般响应：

text
FE DC BA | control | command | lenHi lenLo | status | sequence | payload | EF
1

长度字段规则：

  • 请求的 length 覆盖 sequence + payload；
  • 响应的 length 覆盖 status + sequence + payload；
  • length 不包含 magic、control、command、length 自身和 EF；
  • EF 是固定尾部，不是 checksum；
  • command 当前都是 1 字节，不需要声明 framing.command24。

例如，MMA 电量查询：

text
FE DC BA C4 02 00 05 90 00 00 00 80 EF
1
字节含义
FE DC BAmagic
C4MMA request control
02GetDeviceInfo
00 05length = sequence + payload
90sequence
00 00 00 80查询掩码
EFtrailer

对应响应：

text
FE DC BA 00 02 00 07 00 90 04 07 D5 53 45 EF
1

这里的 length 是 00 07：status(1) + sequence(1) + payload(5)。业务 payload 是最后的 04 07 D5 53 45，不包含 magic、control、command、length、status、sequence 和 trailer。

MMA 路径 ​

认证 ​

MMA 使用第一方扩展 xiaomi.mma.auth，入口为 defaultLinkKey。设备包只声明扩展，不在包内携带算法或可执行代码：

    "framing.segmented",
    "splitter.lengthPrefixed",
    "sequence.increment",
    "session.request",
    "session.extension",
    "session.initializationPolicy"
  ],
  "extensions": [
    {
      "id": "xiaomi.mma.auth",

认证流程：

步骤command请求 payload期望响应
challenge0x5001 + 16 字节随机数01 + 16 字节变换结果

挑战随机数由宿主扩展生成。当前实现只支持第三方兼容路径使用的固定默认 link key，动态 setLinkKey 尚未实现。

认证是 required initialization 的第一步。挑战变换不匹配或完成响应不正确时，会话进入 InitializationFailed 并关闭 RFCOMM transport；不会用未认证状态继续查询设备。

查询与配置 ​

功能command请求 payload响应或说明
查询设备信息 / 电量0x0200 00 00 80匹配 04 07 LL RR CC
读取配置0xF300 0B噪声控制配置 ID 为 0x000B
写入配置0xF204 00 0B mode 00发送后尽力回读 0xF3

电量字段 LL、RR、CC 分别表示左耳、右耳和充电盒：

  • bit 7 是充电标志；
  • bit 0..6 是 0–100 的百分比；
  • 0xFF 表示该路电量不可用。

当前通用 MMA 包直接读取低 7 位。新包如果设备会返回 0xFF，应像 Redmi Buds 6 包一样保留上一次状态，而不是显示 127%。

噪声模式值：

值状态
0关闭
1降噪
2通透
255不支持

写入配置后通过 refresh: ["noise.get"] 回读。回读是尽力执行：写入已经成功时，回读超时不会反转写动作的结果。

Redmi Buds 6 / RCSP TargetInfo ​

Redmi Buds 6 样例不执行 MMA 挑战应答。它使用精确名称 matcher、从序列号 0 开始的 RCSP 请求，并区分普通响应与设备主动通知。

text

它的 command 是 0x0E，length 是 0x0004，payload 是 02 04 01。因为 control 是 C7，这一帧走 request 布局，没有 response 的 status 字节。

TargetInfo 命令 ​

功能commandpayload说明
查询 TargetInfo0x0200 00 00 80回包包含电量 TLV
设置降噪0x0802 04 mode02 为 TargetInfo，04 为 ANC，mode 为 0–2
状态通知0x0E04 LL RR CC 或 02 04 mode设备主动发送

TargetInfo TLV 的基本结构是：

text
length | type | data
1

length 包含 type 字节，但不包含 length 自身。因此 04 07 D5 53 45 表示：

  • length = 4；
  • type = 7；
  • data = 三个电量字节 D5 53 45。

状态通知中的 02 04 01 表示 length = 2、type = 4、data = 模式 1（降噪）。

防止电量被写操作覆盖 ​

降噪写操作的响应也可能带有 04 前缀。不能让电量 state 只按 payloadPrefix: "04" 匹配，否则一次 ANC 写入可能被解码成三路电量。

Redmi Buds 6 同时限制 command 和 payload：

json
{
  "commands": [2, 14],
  "payloadPrefix": "04"
}

初始化策略 ​

MMA 通用包使用 v5 initialization：

  1. required 的 MMA 认证；
  2. optional 的电量读取；
  3. optional 的噪声模式读取。

认证失败会关闭会话；后两项失败只记录并继续。

Redmi Buds 6 使用旧的 initialize 列表。TargetInfo 查询在会话进入 Ready 后尽力执行，因此一次探测超时不会把已经建立的 RFCOMM 会话改成失败。

如果设备必须依赖认证结果才能继续，使用 initialization；如果只是可选的初始状态探测，可使用 initialize，或把 initialization 步骤设为 required: false。

Melody 投影 ​

原生降噪控件需要：

  • state 使用可交互模式，如 ancMode；
  • action 使用稳定名称，如 anc.setMode；
  • ui 中存在读取该状态的 segmented、slider 或 switch；
  • melody.anc 的 state、action 和 protocolIndex 引用真实定义。

Redmi Buds 6 包没有声明 melody.support.productId。这不会让投影失败：宿主会使用稳定的 MAC 派生 ID。何时应声明官方 productId、何时应省略，见 Melody productId。

验证状态与限制 ​

当前仓库的验证边界如下：

  • MMA 默认 link key 变换有 36 组原生库真值向量；
  • MMA 和 RCSP 的黄金帧、单字节切分、粘包恢复、电量、降噪状态和失败路径有 JVM fake RFCOMM 测试；
  • Redmi Buds 6 的 TargetInfo 电量、C7 通知和 ANC 写操作有回归测试；
  • P5 整体尚未记录完整真机验收，不能把 JVM 结果等同于所有型号已在硬件上通过。

新增型号时至少记录设备型号、固件、宿主版本、RFCOMM UUID、完整请求/响应帧以及电量与降噪的实际观察结果。只验证“能连接”不能证明协议字段正确。
